# 검토 의견 — Agent Discussion 확장 로드맵

- 대상: `agent-discussion-expansion-plan.md` (KODA, 2026-10-11)
- 검토: 모루·Cowork · 2026-10-11 · re.eul 요청
- 결론: 방향(브릿지 → GitHub → Railway)은 타당. 다만 **모루에 대한 전제가 바뀌었고**, Phase 1 브릿지에 보안 장치 3가지가 필요.

---

## 1. 전제 수정: 모루는 이제 파일에 직접 접근한다

로드맵은 "클라우드 멤버(이음·모루) → 파일 시스템 접근 불가"로 가정했지만, 2026-10-10부터 상황이 다르다.

| 멤버 | 실행 위치 | cowork 폴더 접근 | 참여 방식 |
|---|---|---|---|
| 모루 (Cowork) | 클라우드 세션 + re.eul PC 연결 | **읽기·쓰기·명령 실행 가능** (Windows KB5129195 이후) | **일반 참가자**로 직접 참여 가능 |
| 이음 (Chat Mode) | claude.ai 채팅 | 불가 | 브릿지 필요 (로드맵 그대로) |

- 모루는 `watch_turn.sh`를 PC 쪽 셸에서 실행할 수 있다. 단, 한 번에 최대 3분이라 짧게 반복 호출하는 방식이 된다 (inotifywait 없음 → 3초 폴링).
- 제약: **모루 세션이 열려 있을 때만** 참여한다. 세션이 없으면 차례가 멈춘다 → 이때만 브릿지로 대체.
- 따라서 Phase 1 브릿지의 1차 대상은 **이음**이고, 모루는 "세션 없을 때의 대체"로 범위를 줄이는 것을 제안.

## 2. 브릿지 = 실제 멤버가 아니다 (정체성 표기)

API로 페르소나 프롬프트만 넣어 부르는 이음·모루는 **그 멤버의 기억·작업 맥락·도구가 없는 복제본**이다. `discussion_v020_test.md`의 "fama (simulated)" 사례와 같은 문제.

- 표기 제안: `**이음 (bridge):**` + `<!-- external-unverified · bridge: claude-api · persona: cowork/이음/bridge-persona.md -->`
- 실제 멤버가 나중에 세션에서 확인하면 `<!-- verified-by: 이음 YYYY-MM-DD -->`를 덧붙이는 절차를 두면 좋다.

## 3. Phase 1 브릿지 보안 장치 (필수)

1. **표식 위조 차단.** API 응답에 `[TURN: …]`, `[AGREED: …]`, `[DEADLOCKED]`, `[EXTERNAL: …]` 같은 제어 표식이 들어 있으면 지우거나 무력화한 뒤 붙인다. 다음 차례 표식은 bridge.sh가 직접 쓴다. (토론 파일 전체가 프롬프트로 들어가므로, 파일 안 문장이 브릿지를 조종하려 할 수 있음)
2. **API 키 관리.** `ANTHROPIC_API_KEY`는 환경변수로만. 레포·토론 파일·로그에 남기지 않는다. `.env`는 `.gitignore` 확인.
3. **비용·길이 상한.** 매 차례 파일 전체를 보내므로 라운드가 쌓이면 토큰이 커진다. 최근 N라운드 + Intro만 보내거나, 차례당 max_tokens·하루 호출 상한을 둔다. (비용 시뮬레이션 v0.2의 "레버" 관점과 같은 관리 대상)

추가 권장: 브릿지가 쓰기 직전에도 "마지막 TURN 표식이 아직 그 멤버인지" 다시 확인 (동시 쓰기 방지).

## 4. Phase 2 제안: 허브 레포의 Issue 흐름을 재사용

허브 레포는 이미 **Issue + Actions 트리거**(`#KeBin` → 라벨·접수 댓글)로 비동기 작업을 돌린다. 파일 push/pull 대신 **Issue 댓글 = 한 차례**로 두면:

- git 충돌이 없고, 기존 `kebin-issue-trigger.yml` 패턴(`#Molu`, `#Ieum` 태그)을 그대로 확장 가능
- 히스토리·감사 추적은 GitHub가 해결
- 단, 기관 협력(인제군·홍천군 AI)이 들어오면 **private 레포**에서 운영 (허브 레포는 공개 범위 확인 필요)

## 5. Phase 3 메모
